## Product review · `6-billing-and-invoicing/SPEC.md` · verdict: **minor changes**

**Strengths**
- Purchases are idempotent per request and statements are computed from the ledger, never stored: honest and cheap to explain.
- P09 statement shows provider cost vs 25% fee, which is a genuine product-sense differentiator.

## Technical review · `6-billing-and-invoicing/SPEC.md` · verdict: **minor changes**

**Strengths**
- Everything customer-facing is derived from the ledger of 3-03, so nothing new can drift. Statements are computed on demand and never stored.
- Purchases are simulated with an explicit idempotency key, a unique constraint and a ledger unique (purchase_id,type), a layered defence.
- Printable HTML instead of a PDF library: the right amount of effort for a take-home. The gapless per-year numbering uses a locked counter row in the same transaction as the purchase.

**Findings**

| # | Severity | Section | Issue | Suggestion | Resolution |
|---|---|---|---|---|---|
| 1 | important | Statements / Billing page (cards) | customers.balance_nanos is 'available' = Σ all ledger entries including hold (-max) and hold_release (+max). A statement 'closing balance' from the ledger therefore moves when a hold is open: a customer who bought $10 and has a $0.09 hold sees $9.91 closing balance, not $10 minus charges. Statement totals (opening, grants, purchases, usage, closing) will not reconcile if holds are excluded from usage but included in the balance. The same issue appears in A09 'Outstanding credits = Σ balances', which understates liability by Σ held. | Define statement balance as Σ of purchase, promo_grant, adjustment and charge entries only (funds, excluding hold and hold_release), and show 'on hold' separately as a point-in-time figure. Define liability as Σ(balance_nanos + held_nanos). Make the test 'opening + grants + purchases + adjustments - charges = closing' use those types, and keep opening(m+1) = closing(m). | ✖ rejected: premised on hold ledger rows, superseded by D-024/D-029 |
| 2 | important | Statements: usage by provider | Time bucketing is ambiguous. The admin Reports (spec 7) group by usage_records.billing_date (provider completion day), while statements use 'the UTC month' of ledger entries. A take completing at 23:59:50 UTC and settled by reconcile after midnight lands in different days/months depending on the source, so the customer statement and admin report disagree, and the 'statement totals equal Σ ledger' test passes while 'statement usage = report usage' fails. | Pick one rule and state it: statements bucket by ledger created_at (UTC) because they must reconcile to the balance; the admin reports bucket by billing_date because they must reconcile to /v1/usage. Label both clearly on the page ('by settlement date' vs 'by provider billing day') and add one test with a take that settles after midnight. | ☑ applied (bucketing rule kept for spent-this-month) |
| 3 | important | Purchases (idempotency) | Unique on purchases.idempotency_key alone has two issues. It is global, so one customer's key can collide with another's (and leak existence via an error). Under a concurrent double-click the second request hits a unique violation as an exception after wasted work, instead of returning the first result. Also, lock order must be explicit: customer first (RecordLedgerEntryAction) then invoice counter, never the reverse. | Use unique(customer_id, idempotency_key). In PurchaseCreditsAction, lock the customer first, then look up the key and return the existing purchase if found (so the second request waits for the first, then replays), and only then insert. Document the order customer -> counter and test two parallel requests with the same key (one purchase, one invoice, one ledger entry). | ☑ applied |
| 4 | important | Invoices: invoice_counters | 'SELECT ... FOR UPDATE on the counter row' fails for the first purchase of a year, as no row exists to lock, and two concurrent first purchases race on insert (duplicate PK or duplicate number). The test 'concurrent purchases produce consecutive numbers' will not cover January 1st. | In IssueInvoiceAction run INSERT ... ON CONFLICT (year) DO NOTHING, then SELECT ... FOR UPDATE, then increment (or a single UPDATE ... RETURNING after the upsert). Test the first-of-year case in parallel. Note in the README that gapless numbering serialises purchases, which is acceptable at this scale. | ☑ applied |
| 5 | important | Welcome credit (D-019) | 'On registration: ledger promo_grant' needs to be atomic with customer creation and idempotent, or a retried registration/verification double-grants. There is no unique rule for it, and the ledger only has unique (usage_record_id,type) and (purchase_id,type). Unlimited self-registration also means unlimited free credit against a shared 500/day Pixelforge quota. | Grant inside the Fortify CreateNewUser action in the same transaction as the customer insert, and add a partial unique index on ledger_entries(customer_id) where type='promo_grant' and reason='welcome'. The seeder must use the same guard so re-running the deploy seed does not top up demo balances. Consider gating the grant on email verification (or a per-IP registration throttle) and a daily cap on new customers (see spec 9). | ✖ rejected: verification gating contradicts D-030; grant moved to spec 4 (D-026) |
| 6 | minor | Billing page: Activity folding | Folding hold + hold_release + charge by reconstructing from ledger rows is brittle (open usages have only the hold, voided ones net to zero, over-estimates give a negative final available). | Drive the Activity list from usage_records joined to the ledger: one line per usage showing status (reserved / charged $X / not charged), and ledger rows only for purchase, promo_grant and adjustment. It is easier to test and explain. | ☑ applied |
| 7 | minor | Statements display | Statements show 4 decimals but are built from nanodollar sums. Summing rounded line items will not equal the rounded total (a visible penny-style mismatch on a printable document), and showing provider cost and 'fee' to customers exposes the 25% rule (fine as a transparency choice, but it is a decision). | Compute totals from exact nanodollars and round only for display, per D-021. On printable invoices and statements show exact values (trailing zeros trimmed) or 6+ decimals. Add a test with figures whose rounded parts do not add up. | ☑ applied (exact display) |
| 8 | minor | Scope / issues list | For a 2-4 h required brief, invoices plus statements plus counters is the largest stretch item and has no evaluator-facing requirement. It could eat the time needed for the required money paths and the admin report (which IS in the brief). | Order the issues by brief value: balance and blocking (already needed), fake Buy credits, then the Billing page, then invoices, then statements last and explicitly droppable. Record the cut line in the spec. | ☑ applied |
