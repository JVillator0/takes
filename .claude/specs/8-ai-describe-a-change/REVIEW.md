## Product review · `8-ai-describe-a-change/SPEC.md` · verdict: **minor changes**

**Strengths**
- AI proposes, human confirms; the diff + rationale + new price is a convincing intuitive-UI story and fits the mission.
- Cost is disclosed up front (about $0.0003, max $0.0007, charged even if discarded) and failures are voided with plain copy.

## Technical review · `8-ai-describe-a-change/SPEC.md` · verdict: **minor changes**

**Strengths**
- Reuses Open/Settle/Void unchanged, so the AI path gets exactly-once billing and a hold for free. Failed or invalid output voids and is never charged.
- Output is treated as untrusted: re-validated with the same rules as StoreTakeRequest, a closed schema, nothing executed. The user confirms before any Pixelforge spend ('The AI never spends Pixelforge money by itself').
- Multiple cost guardrails (kill switch, daily budget, workspace limit) for real money on a public demo.

**Findings**

| # | Severity | Section | Issue | Suggestion | Resolution |
|---|---|---|---|---|---|
| 1 | important | Flow step 2 (CreateSuggestionAction) | The text lists the transaction (lock, insert, OpenUsage) and then 'call the agent synchronously' with no boundary. If the 20 s call runs inside the transaction, the customer row lock is held for 20 s and blocks webhook settlement for that customer. If it runs outside and the process dies after commit, the suggestion stays pending and the Anthropic usage stays open forever (the hold never releases), and there is no scheduler to clean it up. | Specify two transactions: T1 insert suggestion + OpenUsage, commit; call the model with no locks; T2 settle or void. Add expiry: any suggestion pending > 2 min is voided by the same opportunistic sweeper as spec 5 (called on the drawer load and admin Needs attention). Test: kill after T1 -> sweeper voids and releases the hold. | ☑ applied |
| 2 | important | Flow step 2 / POST /takes/{take}/suggestions | No idempotency. A double click or a retried POST calls Anthropic twice and charges twice, and the throttle (6/min) does not prevent it. Spec 4 had the same gap for takes. | Client-generated uuid sent with the request, stored as suggestions.request_key with unique(customer_id, request_key); a replay returns the existing suggestion. Also reject a new request while the same base take has a suggestion in pending. | ☑ applied |
| 3 | important | Money: max hold bound (2,000 input tokens) | The input bound is too tight. A09 shows a typical 1,480 input tokens. The input contains the system instructions, a base prompt up to 4,000 chars (~1,000 tokens), an instruction up to 500 chars, and up to 4 reference URLs of up to 2,048 chars each (~2,000 tokens by themselves). Real inputs can exceed 2,000, so over_estimate fires routinely, available can go negative, and the 'max' is not a maximum. | Make the bound derived from the actual request: input_bound = ceil(utf8 bytes of all input / 2) + a fixed overhead for the system prompt and schema, computed in code, and hold on that. Better: do not send reference URLs to the model at all (it only needs how many references there are; see the next finding), which also cuts tokens and cost. Keep max_tokens = 600 as the output bound. Add a test that an adversarially long input still has hold >= actual. | ☑ applied |
| 4 | important | Agent: structured output schema (reference_images) | The model may return arbitrary http(s) URLs in reference_images. They pass the 'http(s), <= 4' validation but are model-invented, then sent to Pixelforge and billed at 765 tokens each. This is also a prompt-injection vector through the user-controlled URLs in the input. | Replace the field with keep_references: boolean (or indices into the base take's references) and add_base_image_as_reference; the server re-attaches the real URLs. Validate size/quality against enums and the prompt length only. | ☑ applied |
| 5 | important | Money: rates and model claims | The pricing facts cannot be verified from the Pixelforge docs: Haiku 5.5 at $0.10 / $0.50 per 1M, the '< 100K tokens' tier, 'no server-side fallback', and the cache_read/cache_write kinds. The ledger will charge customers 125% of whatever is in config/ai-pricing.php, and A11 treats the Anthropic console as the external cross-check, so a wrong rate is a systematic money error. 'Cache-friendly' instructions are also moot: a few hundred tokens of system prompt is below the minimum cacheable prompt length. | Put the rate source URL and retrieval date in config/ai-pricing.php comments and in the spec, and check the numbers against the Anthropic pricing page and one real call's usage before merge. Drop cache_* kinds and the caching claim (YAGNI). Add a test that the config contains exactly the kinds that the usage extractor can produce. | ☑ applied |
| 6 | important | Guardrails | The daily budget check sums settled Anthropic usage only. Concurrent requests all pass the check before any settles, so the budget can be exceeded by the number of in-flight calls. Four overlapping controls (kill switch, global budget, per-customer 30/day, throttle 6/min) plus the workspace limit is more than a take-home needs and each needs tests. | Count budget as Σ(provider_cost where settled) + Σ(max_cost where open). Keep: kill switch, global daily budget, throttle, and the Anthropic workspace limit. Drop the per-customer 30/day (the throttle and the customer's balance already bound it) or fold it into the throttle. | ☑ applied |
| 7 | minor | Flow step 4 (apply) and tests | 'The proposal can't be applied twice' needs a mechanism, not just a status check. Two concurrent 'Generate take' clicks would both read status proposed. The price shown in the drawer can also be stale by apply time. | In the apply action lock the suggestion (lock order: suggestion -> customer -> usage, as documented), check status = proposed, create the take through CreateTakeAction and set applied in the same transaction. Add a partial unique index on takes(suggestion_id) where suggestion_id is not null. Recompute the estimate at apply time. | ☑ applied |
| 8 | minor | Agent (laravel/ai) | The attribute names, Lab::Anthropic, structured-output API, Agent::fake and the usage object field names are all stated from memory and the spec says to verify during implementation. This is the highest API-accuracy risk and it sits behind a differentiator. | Timebox a 30-minute spike first (issue 1). If the SDK does not expose exact input/output token usage or structured output cleanly, call the Anthropic Messages API through the Http client (about 30 lines, exact usage, trivial to explain and fake with Http::fake). Record the choice in DECISIONS.md. | ☑ applied |
| 9 | minor | Header: dependencies | Depends on 4 and 6, but the AI path needs only the ledger from 3 and the take creation from 4; 6 is a UI dependency. This delays the AI work behind a stretch milestone. | Change to 'Depends on: 3, 4; 6 only for the billing UI row'. | ☑ applied |
