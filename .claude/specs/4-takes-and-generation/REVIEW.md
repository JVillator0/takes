## Technical review · `4-takes-and-generation/SPEC.md` · verdict: **major changes**

**Strengths**
- Hold = max charge reserved in the same transaction as the take insert; creation and submission are separated, so a rate-limited or failed submit never loses money.
- Idempotent job design: skip unless status is pending, and the same Idempotency-Key is reused on every retry. This is safe under SQS-style at-least-once delivery, even if two workers run the same job.
- Outcome table maps every Pixelforge error code to a deterministic behaviour (release with Retry-After vs fail free). It matches the docs (429 variants, 503 Retry-After 2, 400 blocked).
- The estimate endpoint never receives the prompt, only char count, size, quality and ref count. The worked example (373,875,000) is used as a test oracle.

**Findings**

| # | Severity | Section | Issue | Suggestion | Resolution |
|---|---|---|---|---|---|
| 1 | critical | Create take (step 2) / 3-02 takes.idempotency_key | The idempotency_key is generated server-side on each POST. It only protects job retries, not a client double-click, a retried form POST or an Inertia resubmit. Each of those creates a second take, a second hold and a second provider call, which is a duplicate-charge scenario for the user. The brief explicitly lists 'submit retries'. A global unique on a client-supplied uuid would also allow cross-customer collisions. | Have the composer generate a uuid when it opens (regenerate after a successful create) and send it as a hidden field. Make the constraint unique(customer_id, idempotency_key). In CreateTakeAction, lock the customer first, look up by key, and on a hit return the existing take with no new hold. Use that same key as the Pixelforge Idempotency-Key. Add a test that two identical POSTs produce one take, one hold and one provider call. | ☑ applied |
| 2 | critical | Submit outcomes (PixelforgeUnavailable, retryUntil) vs 5 ApplyTakeSnapshotAction | After an ambiguous failure (client timeout or 5xx after the request was sent), Pixelforge may have created the generation. When the 10-minute window expires, FailTakeAction('provider_busy') sets the take to failed (terminal) and voids the usage. A later succeeded webhook or reconcile is then ignored_stale. Pixelforge bills the account (it shows in /v1/usage) while the customer is never charged. That is a silent money leak, and it also breaks the 'ours matches theirs' claim in A04. | Separate definite non-creation (429, 503, 400, which are safe to fail) from ambiguous (timeout, connection error, 5xx). For ambiguous outcomes, do not fail locally at 10 minutes. Keep retrying the same key, which replays safely. Only after a longer cap (e.g. 30 min) with a confirmed replay-or-nothing answer should you fail. Record any success that arrives for a locally-failed take as webhook outcome 'orphan_success' and surface it in Needs attention. State explicitly who absorbs the cost (see the question). | ☑ applied |
| 3 | important | Submit / reconcile dispatch | ReconcileTakeJob is dispatched only after a 202. If SubmitTakeJob is lost (worker crash, queue loss, failed dispatch after commit) the take stays pending forever, and the hold is never released. There is also no scheduler, so nothing else would find it. Dispatching after commit is also not atomic with the insert. | Dispatch a delayed ReconcileTakeJob (60 s) from CreateTakeAction itself, not from the 202 path. For a pending take with no pixelforge_id it should re-dispatch SubmitTakeJob (same key, safe). Add the stuck sweeper described in spec 5 and test 'pending with no job in the queue gets resolved'. | ☑ applied |
| 4 | important | Estimate + 3-03 §4 | Estimate rules are underspecified and have three traps. (1) The client sends 'chars', but JS string.length counts UTF-16 units while Pixelforge counts Unicode characters, so emoji and CJK give different estimates than the server, and the server will not recompute from the same number. (2) The min text bound is not defined. A06 implies floor(est × 0.85) (16 chars → 13) and max ceil(est × 1.15) (→ 19), which should be written down. (3) The 15% is hard-coded as 115/100, but /v1/pricing returns text_token_variance: 0.15, which json_decode turns into a float, violating the 'no floats in money' arch rule. | Count with [...str].length on the client (or Array.from) and mb_strlen($p,'UTF-8') on the server. On submit, recompute the estimate from the real prompt and use that for the hold. Parse variance and characters_per_text_token into integer bps and integers at the DTO boundary (cast via string, never float arithmetic). Specify text_min = floor(est×85/100), text_max = ceil(est×115/100) and add the A06 numbers (54,215,000 / 76,745,000) as a fixture. Use integer ceil-div (intdiv(n + d - 1, d)), not ceil() on floats. | ☑ applied |
| 5 | important | Submit job / rate limits | Pixelforge limits are per account across all keys: 60 req/min, 3 concurrent, 500/day. The deployed demo has public one-click demo logins, so evaluators, bots and the candidate's own dev use share one quota. The spec reacts to 429s only after they occur, every retry counts against the 60/min budget, and many jobs released with the same Retry-After retry in lockstep. Only the per-customer throttle (10/min) exists on the submit side. | (a) Add job middleware (RateLimited with the database cache, ~50/min app-wide). (b) Before calling, skip the call and release(5 + jitter) if the app already has >= 3 takes in queued/processing, which avoids burning requests on a certain 429. (c) Add jitter to release(). (d) Give daily_limit_exceeded a distinct customer message ('provider quota reached, try tomorrow'), not a generic failure. (e) Add a per-customer daily take cap (e.g. 50) so a demo account cannot drain the shared 500/day. | ☑ applied |
| 6 | important | Routes: GET /takes/{take}/image, Persist image, Remix | The image route streams every image through PHP with a session and DB hit. A 24-card grid means 24 PHP requests on a 1 GiB scale-to-zero Flex instance, which wastes compute and cost (spec 9). The Remix text says 'persisted public URL' while the route is owner-only streaming, which is contradictory. Pixelforge does not download reference URLs, so any string works, but the stored URL is surfaced in the take record. | Store image_path on a private bucket and return Storage::temporaryUrl (10-15 min) in TakeResource so the browser fetches directly from object storage. Keep the owner route only as a fallback. For remix references use the provider image_url if still valid, otherwise a temporaryUrl, and state that explicitly. | ☑ applied |
| 7 | important | Submit (outcome table) / queue behaviour | Operational details that bite on Laravel Cloud managed queues. Release-based retries count as attempts, so $tries must not cap the job before retryUntil. HTTP calls must never run inside a DB transaction or while holding the take row lock, or webhooks for the same take block up to the 10 s timeout. 401 invalid_api_key and 409 are mapped to 'fail take free', which blames a customer-visible take for a deployment misconfiguration. | Write the invariants into the spec. Submit uses retryUntil and no tries cap; no lock or transaction is held across createGeneration (lock only to apply the snapshot); 401 triggers a critical log plus keeping the take pending (alert in Needs attention) instead of failing the customer's take; 409/422 mean a bug and fail with failure_code 'internal'. | ☑ applied (401 stays immediate-fail free, D-025; no keep-pending) |
| 8 | minor | Create take: responses and tests | Test list says restricted => 403 but insufficient credits => 422. FormRequest authorize() through Gate::inspect()->authorize() yields 403 for both denial reasons, so the two codes conflict with the 'denied response rendered back to Inertia with its code' idea in 3-01. | Pick one convention: render denials as a redirect back with a validation-style error {code, message} and HTTP 302/422 for Inertia (not 403), and align the tests. Keep 403 only for ownership failures. | ☑ applied |
| 9 | minor | Persist image (PersistTakeImageJob) | 'Retried 3x' can be exhausted within seconds, while the provider URL lives 24 h, so a short outage loses the image permanently. The download target host is not constrained. | Use backoff [30, 300, 3600] with retryUntil = completed_at + 23 h. Only download when the URL host equals the configured Pixelforge host (SSRF guard). Verify the PNG magic bytes and the 20 MB cap while streaming. | ☑ applied |

**Questions for Javier**
- When a submit ends ambiguously (timeout or 5xx) and retries run out, what should happen to the take and the money? Options: A. Keep retrying the same key for up to ~30 min, then fail free and log any late success as 'orphan_success' (the app absorbs the cost, visible in Needs attention) / B. Fail free at 10 min, but allow a late success to re-open and settle the voided usage (customer pays what the provider billed) / C. Fail free at 10 min, ignore late success (current spec). Recommendation: A. It keeps 'failed = free' and exactly-once settlement simple, and makes the rare leak visible and explainable in the interview. B adds a failed->succeeded transition that complicates the state machine.
