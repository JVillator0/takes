- Plan B polling plus no-scheduler reconcile gives robustness without extra infrastructure, and toasts/live indicator are specified.

## Technical review · `5-webhooks-and-live-status/SPEC.md` · verdict: **major changes**

**Strengths**
- Signature verification follows the docs: raw body, constant-time compare, multiple v1 values, 300 s tolerance, outside the web group. A fresh timestamp per attempt means retries pass the tolerance check.
- Dedup is inside the same transaction as the apply, so a failed apply rolls back the event row and Pixelforge's retry is processed (the desired semantics). Concurrent duplicates serialise on the unique index.
- One ApplyTakeSnapshotAction shared by submit, webhook, reconcile and the admin 'Reconcile now' keeps the money path single and explainable. It handles webhook-before-create via metadata.app_take_id.
- Plan B polling is built in, and a broadcast failure is isolated from the webhook response.

**Findings**

| # | Severity | Section | Issue | Suggestion | Resolution |
|---|---|---|---|---|---|
| 1 | critical | webhook_events table vs wireframes A06/A11 | The spec stores only the first delivery of each event (unique event_id; 'duplicates counted from logs'). But A06 shows per-take deliveries with Attempt 1/2 and outcome 'duplicate', and A11 has a 'Duplicates: 22' stat, an Attempt column and a 'duplicate' outcome row. With one row per event_id those rows and numbers cannot exist, and a log-based count cannot back an admin widget. The spec also lists no 'duplicate' value for the stored outcome. The admin evidence for 'never record the same event twice' would be missing. | Keep webhook_events unique on event_id (the 'recorded once' proof) and add an append-only webhook_deliveries(id, event_id, attempt, outcome, received_at) written for every verified delivery, including duplicates (outcome 'duplicate'). The A06 and A11 tables and the Duplicates stat then read from it. A cheaper alternative is a 'deliveries' counter and 'last_attempt' on webhook_events, but then the per-delivery rows in A06 must change. Update both wireframe and spec to match. | ☑ applied |
| 2 | important | Live status: TakeUpdated (ShouldBroadcastNow) in the webhook request | rescue() catches exceptions, not latency. With ShouldBroadcastNow the Reverb HTTP push runs synchronously inside the webhook request. If Reverb is down or slow (cold, or option C/A deployments), the Pusher client's default timeout can push the response past Pixelforge's 10 s deadline, causing a retry storm of duplicates. The claim 'answers in < 1 s' is unsupported. | Either broadcast through the queue (ShouldBroadcast + dispatch after commit, so the webhook only enqueues), or set a 1-2 s timeout in the reverb connection's client_options and keep rescue(). Add a test that a throwing/slow broadcaster does not change the status code, and note the timeout in the spec. | ☑ applied |
| 3 | important | Reconcile (polling safety net) | A single self-redispatching delayed job is a fragile safety net. If one dispatch fails, the worker dies mid-job, or a message is lost, the chain ends silently and the take stays non-terminal until someone opens it. There is no recovery for a take without pixelforge_id (pending), and no handling for GET returning 404 or for 429s from Pixelforge's own limiter. The 6 h cap is far beyond Pixelforge's behaviour (completion in <= 90 s, webhook retries over ~27 min). Queued 15-min delays are exactly at the managed-queue limit. | (a) Cap at ~30-45 min then 'Needs attention'. Use delays 60 s, 2 m, 5 m, 10 m, 14 m (strictly <= 900 s). (b) Add a stateless sweeper, an idempotent action that dispatches ReconcileTakeJob for non-terminal takes older than N min, called opportunistically from the workspace and admin dashboard loads under a Cache::lock throttle (no scheduler or compute cost), plus the existing artisan command. (c) ReconcileTakeJob handles pending (resubmit same key) and 404 (flag, stop). (d) Use ShouldBeUnique by take id to avoid parallel chains. | ☑ applied |
| 4 | important | ApplyTakeSnapshotAction (steps 2-4) | Several edge cases are unspecified. (1) A 'succeeded' snapshot with null usage (never in docs, but poll/webhook may be a partial object) would settle zero cost for a succeeded take. (2) Rates must come from snapshot.rates of the terminal snapshot, not from the cached /v1/pricing used for the estimate, since rates may change within the 1 h cache. (3) Outcomes for non-terminal same-state events (e.g. duplicate 'processing' with different event ids) are not named: ignored_stale vs ignored_same_state. (4) failed arriving for a take already failed locally, and succeeded arriving for a locally failed take, need a defined outcome. | Add: succeeded with null usage or missing rates => no state change, outcome 'invalid_snapshot', log critical, flagged for attention. Settle using snapshot.rates only. Define the outcome matrix explicitly (current x incoming -> outcome) as a table next to the state machine and drive the test table from it. Add outcome 'orphan_success' (see spec 4). | ☑ applied |
| 5 | important | Live status: Echo/poll fallback | Detecting 'Echo not connected' (to start polling) is the most complex piece of the frontend and the hardest to test (needs connection state hooks and reconnect logic). It exists for a failure mode that webhooks + reconcile already cover server-side. Also the channel authorisation depends on the default guard; guards are not declared on the channel, and the event name depends on the class namespace, which is a common cause of 'event never arrives'. | Simplify: always poll (usePoll 5-10 s, only: ['takes','counts','auth']) while any take is non-terminal and the tab is visible, in addition to Echo, and drop connection-state detection. When Echo is working the poll is a cheap belt-and-braces. Declare Broadcast::channel('App.Models.Customer.{id}', fn, ['guards' => ['customer']]) and set broadcastAs() on TakeUpdated. When BROADCAST_CONNECTION is log, expose a boolean so the client never starts Echo (spec 9). | ✖ rejected: D-028 keeps connection-based fallback, no env switch (guard + broadcastAs applied) |
| 6 | minor | Endpoint / signature details | Minor hardening items. A missing or zero t must fail; a header with no v1 must fail (not match an empty string via hash_equals on ''); the secret should be compared as string values only; the status code is 401 where the docs example uses 400, which is fine because any non-2xx is retried, but the choice should be recorded. Malformed JSON and unknown types should return 200 (outcome 'ignored_type') so Pixelforge does not retry unactionable events. | Add tests: header without v1, non-numeric t, two v1 values where the second is valid, unknown event type => 200 'ignored_type', invalid JSON with valid signature => 400. Document the 401 choice. | ☑ applied |
| 7 | minor | HandlePixelforgeWebhookAction ordering | The transaction order is insert event -> lock take. Together with take -> customer -> usage, there is no deadlock cycle, but the doc never states that an exception in Apply must propagate (rolling back the event row and returning 500) so retries redeliver. A swallowed exception would permanently lose the event because the dedup row would be committed. | State 'never catch inside the transaction; map to 500'. Add a test that forces SettleUsageAction to throw and asserts there is no webhook_events row and a 5xx, then a retried delivery settles once. | ☑ applied |

**Questions for Javier**
- How do you close the 'lost job' gap without a scheduler? Options: A. Opportunistic sweeper called from workspace and admin page loads (throttled with Cache::lock), plus the self-chaining job / B. Laravel Cloud scheduler running takes:reconcile --stale every 5 minutes (keeps compute and DB awake) / C. Only the self-chaining job (current spec). Recommendation: A. It costs nothing, survives lost chains for any evaluator who looks at the app, and is easy to explain. If the budget allows, B can be added after review.
