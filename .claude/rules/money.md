# Money rules (checklist)

Source: spec 3-03 (money and ledger), 3-02 (state machine), 8 (AI suggestions), decisions D-002, D-015, D-021, D-023, D-024, D-025, D-033, D-042, D-055, D-059.
Applies to: `app/Support/Money`, `app/Actions/Billing`, `app/Actions/Takes`, `app/Actions/Suggestions`, `app/Jobs`, `app/Http/Resources`, `app/Policies`, `config/takes.php`, `config/ai-pricing.php`, `database/migrations`, and any code that reads or writes an amount.

Every rule has an ID, the violation reviewers reject, and the test that enforces it. A PR that adds a rule or a test path updates this file in the same PR. A test path listed here that does not exist yet is created by the spec issue that first touches the rule; until then the reviewer checks the rule by reading the diff.

Reviewers: a violation of any rule below is a **critical** finding unless the rule says otherwise.

## Unit and arithmetic

- [ ] **M-01 Integer nanodollars.** Every amount is an `int` of nanodollars (10⁻⁹ USD) in PHP and a `bigint` in Postgres, wrapped in `App\Support\Money\Nanodollars` when it travels. Columns end in `_nanos`.
  Reject: `float`, `decimal`, `double`, cents, or a USD string stored or passed between layers.
  Tests: `tests/Unit/Money/NanodollarsTest.php`.
- [ ] **M-02 No floats in money code.** No `float` type, `floatval`, `(float)`, `round(`, `number_format(`, `/` on amounts, or `bcmath` in `App\Support\Money`, `App\Actions\Billing`, `App\Actions\Takes`, `App\Actions\Suggestions`. Display rounding exists only in `Nanodollars::format()`, built with `intdiv` + remainder.
  Tests: `tests/Arch/ArchitectureTest.php` (money float scan); `tests/Unit/Money/NanodollarsTest.php` (rounding boundaries x.49999, x.5, exact; its own no-float check is the shared `SourceScan::floatViolations`).
- [ ] **M-03 Rates and USD config are strings.** Rates in `config/ai-pricing.php` and USD env values (`WELCOME_CREDIT_USD`, `AI_DAILY_BUDGET_USD`) are decimal strings parsed once through `Nanodollars::fromDecimalString` / `perMillionFromDecimalString` (D-066). Nothing downstream sees a float or a USD string.
  Tests: `tests/Arch/RepositoryTest.php` (float scan over `config/`); `tests/Unit/Config/TakesConfigTest.php` (`AI_DAILY_BUDGET_USD=0.5` gives `500_000_000`).
- [ ] **M-04 SQL sums go through `Nanodollars::fromInt(int|string)`.** Postgres `SUM(bigint)` returns `numeric`, which PDO gives as a string; never cast it with `(int)` after a float, never `(float)`.
  Tests: `tests/Unit/Money/NanodollarsTest.php` (`fromInt` with integer strings).
- [ ] **M-05 Cost and charge formulas.** `cost = ceil(Σ(units_k × rate_k) / 1_000_000)`; `charge = ceil(cost × (10_000 + markup_bps) / 10_000)` with `markup_bps = 2500` snapshotted on the usage record. Integer arithmetic only. Failed work: cost 0, charge 0.
  Tests: `tests/Unit/Billing/TakeEstimatorTest.php` (docs worked example: 400 chars, high, 1536×1024, 2 refs ⇒ cost 373,875,000; markup exactness for every kind; ceil guard with a synthetic odd rate; `mb_strlen` with accents and emoji); `tests/Unit/Money/TokenCostTest.php` (formula, zero-count kinds need no rate); `tests/Unit/Billing/ChargeExactnessTest.php` (markup exactness for every kind, charge ceil); `tests/Feature/Billing/UsageActionsTest.php` (settle amounts, ceil warning with usage context, Anthropic zero-count kinds).

## Ledger and holds

- [ ] **M-06 Holds are state, not ledger rows (D-024).** An open usage record's `max_charge_nanos` is the hold. `customers.held_nanos` = Σ open holds, `customers.balance_nanos` = Σ ledger, `available = balance − held`. Ledger types are exactly `purchase`, `promo_grant`, `charge`, `adjustment`.
  Reject: a `hold` / `release` ledger type, a ledger row written on open or void, `available` stored as a column.
  Tests: `tests/Feature/Billing/LedgerInvariantTest.php` (randomized sequence ⇒ Σ ledger == balance and Σ open `max_charge` == held); `tests/Feature/Billing/VerifyBillingCommandTest.php` (passes on clean data, fails on injected drift, including an open usage on a terminal take or on a suggestion whose AI call is over); `tests/Feature/Billing/ListLedgerInvariantViolationsQueryTest.php` (the bounded variant for page loads re-prices only its window and keeps the SQL checks over every row).
- [ ] **M-07 One writer of the ledger.** `RecordLedgerEntryAction` is the only code that inserts `ledger_entries` or changes `customers.balance_nanos`; only `OpenUsageAction`, `SettleUsageAction`, `VoidUsageAction` change `held_nanos`. Ledger rows are append-only (the model throws on update and delete). Admin adjustments write an `adjustment` row, never edit a balance.
  Tests: `tests/Feature/Billing/RecordLedgerEntryActionTest.php`; `tests/Arch/ArchitectureTest.php` (no `balance_nanos` / `held_nanos` writes outside `App\Actions\Billing`, via `SourceScan::columnWrites`; in `app/Models` only the `$attributes` defaults and the `casts()` body are set aside, so a model method or hook that assigns, increments or `forceFill`s the column fails).
- [ ] **M-08 Database backs the invariants.** Unique `(usage_record_id) where type = 'charge'` (a usage is charged once); unique `(purchase_id) where type = 'purchase'`; unique welcome `promo_grant` per customer; sign CHECKs (purchase/promo_grant > 0, charge < 0, adjustment ≠ 0); `usage_records` status CHECKs (open ⇒ cost/charge null; settled ⇒ not null; voided ⇒ both 0; `absorbed_cost_nanos` only on a voided usage, ≥ 0, with a billing date; D-087); `suggestions.failure_reason` CHECK from `SuggestionFailureReason`; `customers.held_nanos >= 0`; FKs on money rows are `restrict`, customers are never hard-deleted. Migrations are reversible.
  Tests: `tests/Feature/Database/MoneyConstraintsTest.php` (raw inserts rejected); `tests/Feature/Database/SuggestionFailureReasonCheckTest.php`; `tests/Feature/Database/MigrationsTest.php` (up/down).

## Transactions, locks and settlement

- [ ] **M-09 Money actions run inside the caller's transaction.** `OpenUsageAction`, `SettleUsageAction`, `VoidUsageAction` (and `RecordLedgerEntryAction`, `IssueInvoiceAction`) start with `TransactionRequiredException::unlessInTransaction()`, a real exception that holds with `zend.assertions` off, and never open their own outer transaction.
  Tests: `tests/Committed/TransactionGuardTest.php` (each action throws at transaction level 0 and writes nothing; outside the `RefreshDatabase` suite, which always has a transaction open).
- [ ] **M-10 Lock order: take | suggestion → customer.** The caller locks the take (or suggestion) first with `lockForUpdate()`; the money actions then lock **only the customer row**; the usage record is **re-read under the customer lock, never locked separately**. Any new caller follows the same order. A take created with a parent (remix, Try again, AI apply) locks the parent take `FOR KEY SHARE` before the customer (an AI apply: suggestion → parent take → customer): exactly the lock the lineage FK insert needs, it still waits for a parent being settled (`FOR UPDATE`, take → customer), and it is compatible with the key-share `CreateSuggestionAction` T1 takes on its base take after the customer, so neither order forms a cycle. Never `FOR UPDATE` on a parent before the customer: that deadlocks (40P01) with Describe a change on the same take.
  Reject: `lockForUpdate()` on `UsageRecord`; locking the customer before the take/suggestion; reading usage status before taking the customer lock and trusting it afterwards.
  Purchases (spec 6) lock **customer → invoice counter** and never the reverse: `IssueInvoiceAction` increments the year's `invoice_counters` row under its row lock after the customer lock, so numbers are gapless per year.
  Tests: `tests/Committed/ConcurrencyTest.php` (group `concurrency`, two real processes, a late worker fails the test: two opens for a balance that covers one ⇒ one `InsufficientCreditsException` and one open usage; two settles of different takes of one customer in parallel ⇒ exact balance); `tests/Committed/RemixSuggestionLockRaceTest.php` (group `concurrency`: a remix of take P and Describe a change on P at once ⇒ both finish, no 40P01; a late worker fails the test); `tests/Arch/ArchitectureTest.php` (no `lockForUpdate` / `sharedLock` on usage records, via `SourceScan::usageRecordLocks`); `tests/Committed/InvoiceConcurrencyTest.php` (group `concurrency`: parallel purchases get consecutive numbers, including the first purchases of a new year; a same-key double-click creates one purchase, one ledger entry and one invoice); `tests/Committed/SuggestionConcurrencyTest.php` (group `concurrency`, a late worker fails the test: two suggestions racing on a balance that covers one hold ⇒ one `proposed`, one `insufficient_credits`).
- [ ] **M-11 Take transitions only in `ApplyTakeSnapshotAction` and `FailTakeAction`.** No other class writes `takes.status`. Both lock the take, set `last_event_at` and return a `TransitionOutcome`.
  Reject: `$take->status = …`, `update(['status' => …])` or `forceFill(['status' => …])` anywhere else (controllers, jobs, listeners, Filament actions, seeders outside factories).
  Tests: `tests/Feature/Takes/ApplyTakeSnapshotActionTest.php` (full transition matrix, every outcome); `tests/Feature/Takes/FailTakeActionTest.php`; `tests/Arch/ArchitectureTest.php` (status writes only in the two actions, via `SourceScan::takeStatusWrites`: TakeStatus cases or their strings anywhere, models included apart from their declared `$attributes` default; any value in a file that references `Take`).
- [ ] **M-12 Settlement exactly once, inside the terminal transition.** A take's usage is settled (succeeded) or voided (failed) in the same transaction that moves the take to a terminal state, and nowhere else. A suggestion's usage is settled or voided only in `CreateSuggestionAction` T2 or by `ExpireSuggestionAction` (spec 8 expiry: lazily before T1 for the customer's expired pending suggestions, and by the spec 5 sweeper). Settling or voiding a non-open usage is a silent no-op, never an exception that could break a webhook. One exception, not a money change: a void that carries units the provider still billed records them as `absorbed_cost_nanos` on a voided usage that has none yet (an AI result after expiry, D-087); it never touches a settled usage, a hold or the ledger.
  Tests: `tests/Feature/Billing/UsageActionsTest.php` (settle twice ⇒ one charge; settle after void ⇒ no-op; void after settle ⇒ no-op; re-open of a closed usage throws; absorb on an open usage, on a voided usage once, never twice, never on a settled one); `tests/Feature/Webhooks/WebhookIdempotencyTest.php` (duplicate delivery ⇒ one settlement); `tests/Feature/Takes/ApplyTakeSnapshotActionTest.php` (same success applied twice ⇒ one charge); `tests/Committed/TakeTransitionConcurrencyTest.php` (group `concurrency`: two processes apply the same success ⇒ `applied` + `ignored_same_state`, one charge; a late worker fails the test); `tests/Feature/Takes/TakeMoneyFlowTest.php` (signed success delivered twice ⇒ one charge of cost × 1.25).
- [ ] **M-13 Failed = free.** Every failure path voids the usage and releases the hold: provider `failed`, definite rejections, `cancelled`, `provider_busy`, `submit_timeout`, `internal`, revoked key (D-062), AI error/refusal/timeout. An AI call the provider still billed (refusal, `max_tokens`, invalid output, a result after expiry) is voided with its tokens, `absorbed_cost_nanos` and `billing_date` (admin-only, never charged), which the global daily AI budget counts on its `billing_date` (spec 8, D-087).
  Tests: `tests/Feature/Takes/FailTakeActionTest.php`; `tests/Feature/Takes/TakeMoneyFlowTest.php` (compose → submit → webhook, failed and rejected are free); `tests/Feature/Takes/SubmitTakeJobTest.php` (every submit failure path); `tests/Feature/Webhooks/WebhookOutcomeMatrixTest.php` (`failed` ⇒ not charged, hold released); `tests/Feature/Suggestions/CreateSuggestionActionTest.php` (every AI failure path, and a suggestion orphaned after T1 expired ⇒ voided; billed tokens of a voided call count toward the budget); `tests/Feature/Suggestions/ExpireSuggestionActionTest.php`; `tests/Feature/Billing/GetDailyAiSpendQueryTest.php`.
- [ ] **M-14 Orphan success is not settled (D-025, D-049).** A late `succeeded` for a take failed with `submit_timeout`, or with `internal` after Pixelforge accepted it (it had a `pixelforge_id` when it failed; a failed take adopts a generation id only as an orphan, D-077) or while its submit was in doubt (`Take::submitWasInDoubt()` when it failed: kind `ambiguous`, or null with `submit_attempts > 0`; D-082), leaves the usage voided, flags `orphan`, sets `attention_reason = orphan_success` (never overwritten by a weaker reason). After `provider_busy`/`cancelled`, or `internal` after capacity answers only or before any submit attempt, it is `ignored_conflict`. The absorbed provider cost (units × the generation's own rates, never cached prices) is recorded once on the voided usage (`absorbed_cost_nanos`, token columns, `billing_date`), never in the ledger; an unpriced orphan snapshot without rates throws `SnapshotRatesMissingException` with nothing written, and the generation is fetched and applied (D-077(a)); if the fetched generation has no rates either, the orphan is still recorded (flag, `orphan_success`, generation adopted) with its cost left null and a critical log; `billing:verify --usage` adds it to the settled cost of that day and prints the day as "Orphan success (cost absorbed)" (D-058), not as drift.
  Tests: `tests/Feature/Takes/ApplyTakeSnapshotActionTest.php` (orphan vs conflict split; `internal` with `ambiguous` or an unanswered attempt ⇒ orphan on every replay, with `capacity` or no attempt ⇒ conflict; absorbed cost recorded once; an unpriced orphan without rates throws, a priced one re-flags); `tests/Feature/Webhooks/ReconcileTakeJobTest.php` (the fetch prices an orphan that arrived without rates; a fetched generation without rates still records the orphan, without cost); `tests/Feature/Webhooks/WebhookOutcomeMatrixTest.php`; `tests/Feature/Billing/VerifyBillingCommandTest.php` (orphan day on its own line; a differing total still fails).
- [ ] **M-15 Actual > hold still charges the actual amount.** Charge the computed amount, let `available` go negative by the difference, flag `over_estimate`; `TakePolicy` then denies with `insufficient_credits`.
  Tests: `tests/Feature/Billing/UsageActionsTest.php` (over-estimate case).
- [ ] **M-16 No HTTP call inside a database transaction.** Provider calls (Pixelforge create/get, Anthropic) happen with no transaction open and no row locked; the result is applied in a new transaction afterwards (submit job, reconcile job, `CreateSuggestionAction` T1 → call → T2).
  Reject: `Http::`, `PixelforgeClient`, or the AI agent called inside `DB::transaction()` or after `lockForUpdate()`.
  Tests: `tests/Feature/Billing/NoHttpInTransactionTest.php` (`Http::fake` callbacks assert `DB::transactionLevel() === 0` for submit and reconcile); suggestions: `tests/Feature/Suggestions/CreateSuggestionActionTest.php` (the Messages API fake asserts the call adds no transaction and the hold is already placed) and `tests/Committed/SuggestionTransactionGuardTest.php` (`CreateSuggestionAction` throws `TransactionNotAllowedException` inside a caller's transaction, before any call or hold); `tests/Feature/Takes/SubmitTakeJobTest.php` (no transaction during the create call); `tests/Committed/CreateTakePricingTest.php` (pricing fetched before the create transaction).
- [ ] **M-17 No queue delay above 900 s.** Every `delay`, `backoff`, `release()` and `retryUntil` step is ≤ 900 s (Laravel Cloud managed-queue limit). Long waits are chains of short delays (reconcile: 60, 120, 300, 600, 840 s).
  Tests: `tests/Arch/RepositoryTest.php` (max job delay/backoff 900 s for every job).

## Idempotency and authorization

- [ ] **M-18 Every money-creating request is idempotent.** Takes: unique `(customer_id, idempotency_key)`, composer-minted uuid, reused as Pixelforge's `Idempotency-Key`; a replay returns the existing take with no new hold (D-033). Suggestions: unique `(customer_id, request_key)`; the same key on another base take ⇒ 409. Purchases: unique `(customer_id, idempotency_key)`. AI apply: uuid v5 of the suggestion id + partial unique `takes(suggestion_id)`.
  Tests: `tests/Feature/Takes/CreateTakeIdempotencyTest.php`; `tests/Feature/Billing/PurchaseCreditsTest.php` (replay creates nothing; same key with another pack ⇒ 409); `tests/Feature/Billing/InvoicesTest.php` (a replay creates no second invoice; one invoice per purchase); `tests/Feature/Suggestions/ApplySuggestionActionTest.php` (sequential replay, deterministic key, partial unique index); `tests/Feature/Suggestions/CreateSuggestionActionTest.php` (same `request_key` ⇒ no second call or hold; reused for another take ⇒ 409). Spec 8's "two concurrent applies create one take" (group `concurrency`, `tests/Committed`) lands with spec 4's `CreatesSuggestedTake` binding, the first point where apply creates a real take (issue #76); `tests/Feature/Takes/ApplySuggestionCreatesTakeTest.php` (apply through spec 4's CreateTakeAction: one held take with the suggestion lineage, replayed on a second apply); `tests/Committed/ApplySuggestionConcurrencyTest.php` (group `concurrency`: two processes apply one suggestion ⇒ one take, one hold; a late worker fails the test).
- [ ] **M-19 Credits are state, checked twice (D-015).** Policies deny with `Response::deny` and a `DenialReason` code; the action re-checks `available ≥ maxCharge` under the customer lock (`InsufficientCreditsException`). Never grant or revoke a permission because of the balance.
  Tests: `tests/Feature/Takes/TakePolicyTest.php`; `tests/Feature/Billing/UsageActionsTest.php` (open under the lock: exact boundary, 1 nanodollar short ⇒ `InsufficientCreditsException`).

## Display and disclosure

- [ ] **M-20 The server formats money; the frontend never does money math.** Resources and broadcast payloads send formatted strings (and, where needed, integer nanos as strings); Vue never parses, sums, rounds or formats an amount.
  Tests: `tests/Feature/Takes/TakeRoutesTest.php` (money fields are strings, 4 decimals on the card, exact in the drawer); `tests/Feature/Takes/EstimateEndpointTest.php`.
- [ ] **M-21 Exact amounts keep at least 2 decimals.** Money pages (take detail, billing page, invoices) and the admin use `Nanodollars::formatExact()`: trailing zeros trimmed, never fewer than 2 decimals (`$5.00`, `$0.0735`).
  Tests: `tests/Unit/Money/NanodollarsTest.php` (`formatExact` cases); `tests/Feature/Billing/BillingPageTest.php` and `tests/Feature/Billing/InvoicePageTest.php` (exact amounts whose 4-decimal rounding differs).
- [ ] **M-22 Rounded display is never 2 decimals (D-042, D-021).** Lists, cards, toasts and the balance pill use `Nanodollars::format(4, …)`: estimate min rounded down, max rounded up, charges half-up; on the balance pill, on hold (a sum of maximum charges) rounds up like "Up to" and available rounds down, so a negative available and the negative-balance banner's debt both round the debt up (`BalanceSummaryDTO`, the only formatter for the pill, shared `auth` and the live payload); exact value on hover. Totals are rounded from the exact sum, never summed from rounded parts.
  Tests: `tests/Unit/Money/NanodollarsTest.php` (`format` boundaries); `tests/Feature/Takes/TakeRoutesTest.php` (rounded fields have 4 decimals); `tests/Unit/Billing/BalanceSummaryDTOTest.php` (pill rounding).
- [ ] **M-23 Customers never see provider cost, tokens, provider names or margin (D-023).** Customer-facing Inertia props, resources, broadcast payloads, lang strings and error messages expose prices only (estimate range, amount charged, spend by feature: images, AI suggestions). Provider cost, token counts, `pixelforge` / `anthropic`, markup and margin are admin-only.
  Tests: `tests/Feature/Customer/NoProviderLeakTest.php` (scans customer page props and the `TakeUpdated` payload for forbidden keys and words); `tests/Feature/Billing/BillingNoProviderLeakTest.php` (billing page and invoice props).

## Adding a billable provider

  Tests: the provider's estimator test plus `tests/Feature/Billing/LedgerInvariantTest.php`.
